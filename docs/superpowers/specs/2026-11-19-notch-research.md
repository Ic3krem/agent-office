### Window creation (desktop/main.mjs:249-266 `showIsland`)

- Options (main.mjs:251-255): `transparent:true, frame:false, resizable:false, movable:false, skipTaskbar:true, alwaysOnTop:true, hasShadow:false, focusable:true, show:false`; webPreferences contextIsolation, sandbox, no nodeIntegration, webSecurity, autoplayPolicy no-user-gesture-required.
- After creation: `setAlwaysOnTop(true,'screen-saver')` (257), `setVisibleOnAllWorkspaces(true)` (258), `setIgnoreMouseEvents(true,{forward:true})` (259) = click-through by default; shown with `showInactive()` on ready-to-show (263) so it never steals focus.
- NO blur/vibrancy/backgroundMaterial anywhere (grep of desktop/ and package.json found none). Background is a solid CSS colour `var(--bg)` (island.html:12). So today's look is opaque dark pill with an inner 1px glow border (island.html:15-19) and a drop shadow (island.html:12) - not glass.
- Placement: `placeIsland` (241-246) calls setBounds twice because Windows mis-sizes the first call on a display with a different DPI scale. Follows cursor display by default (`pickDisplay`, island-logic.mjs:12; cursorLoop main.mjs:518 every 1 s, 200 ms in smart mode). Tray lets user pin to primary or a display id (main.mjs:589-591). Display add/remove/metrics events call `resync` (554).
- Click-through mechanism: page listens to mousemove, and when the pointer is over `[data-hit]` (the pill) it sends `island:interactive true` (island.html:477-481), main flips `setIgnoreMouseEvents(!on,{forward:true})` (main.mjs:432). Collapsed-and-settled drops back to click-through (island.html:145).
- Per-OS: window options are identical on all OSes. Windows-only parts: fullscreen detection (main.mjs:490-505, resident PowerShell polling `SHQueryUserNotificationState` every 1.5 s; states 2,3,4 count as fullscreen, island-logic.mjs:32) and now-playing/SMTC (nowplaying.ps1; nowplaying.mjs:35 comment "Windows only; elsewhere start() is a no-op"). On macOS/Linux Smart mode is idle-only (docs/island-spec.md:33). `setVisibleOnAllWorkspaces` matters on macOS; Linux/Wayland always-on-top is not supported by Electron (see Part 3).
- Notch off destroys the window (destroyIsland main.mjs:248), stopping pollers.

### Shared design patterns (synthesised from READMEs; source code not read)
- Two or three states: collapsed (hardware notch size or small pill) -> compact "live activity" -> expanded panel. Ripple names them Still / Quick / Large; eIsland Idle / Hover / Expanded / Max Expand; Atoll hover to expand, click to enter controls.
- Triggers: hover (with configurable delay; MewNotch, boring.notch minimumHoverDuration 0.3 s [V Constants.swift]), click, global hotkey, two-finger swipe down/up (Atoll), horizontal swipe for prev/next track, scroll to switch panel (Nectar).
- Layout: tab or panel strip (Music / Calendar / Shelf / Status / Control Center in Nectar; Home / Calendar / Settings in Tiro). Live activities show icon left and value right of the notch (Atoll, Peninsula notification icon then count).
- Drag-and-drop shelf with AirDrop (boring.notch, NotchDrop, MewNotch, Atoll, Peninsula Tray, V-Notch, Nectar).
- HUD replacement for volume/brightness/keyboard backlight (MewNotch suppresses stock HUD; boring.notch roadmap; Alcove customisable HUDs).
- Calendar with meeting join buttons (NotchNook), timers/stopwatch/Pomodoro (Nectar, Atoll, windows-notch-overlay, Peninsula text parsing "2h15m"), clipboard history (Atoll, Ripple, V-Notch), notes/todo (NotchNook, Ripple, eIsland), media with visualizer, lyrics and cover art (all), battery/charging and Bluetooth alerts (Atoll, Ripple), privacy indicators mic/camera (Atoll, Lumen), system stats CPU/GPU/mem (Atoll, windows-notch-overlay, V-Notch), AI usage/approvals (NotchNook Pro, V-Notch, EchoIsland).
- Auto-hide over fullscreen (Nectar, Lumen, Tiro), click-through when idle (Lumen, Nectar, Tiro), pause expensive work when hidden (Nectar, MewNotch "throttled background updates", Tiro power saver).
- Glass and blur: macOS apps rely on SwiftUI/AppKit materials (not described in READMEs [U]); NotchNook Pro and DynamicLake advertise "Liquid Glass" (Apple's macOS 26 material). Windows: V-Notch builds its own blur by duplicating desktop pixels and blurring on GPU; Nectar offers a "glass" style (mechanism not described); FluentFlyout uses Mica via MicaWPF. Nobody in this list documents Electron backgroundMaterial.
- Animation: SwiftUI spring animations (boring.notch, Atoll, Alcove "fluid transitions"); exact spring constants not verified [U] (boring.notch Constants.swift has none; BoringNotch.swift path 404). Nectar says "physics animation". Tiro already uses its own damped spring (k 140-380, c 13-34), comparable. Corner shape: concave top corners blending into the bezel on Mac; Tiro uses square top and round bottom; real notch-style needs inverted top corners (CSS clip-path / SVG path) [design observation, not from a source].
- Customisation: per-feature toggles, layouts (boring.notch, Atoll, MewNotch "custom layout"), settings as JSON (Nectar), per-monitor modes.

### "Accessibility" - both readings

## PART 3 - Feasibility for TiroAgents (Electron 43.8.7)

Electron 43 ships Chromium 150.0.7871.46, Node 24.17.0 [V https://www.electronjs.org/blog/electron-43-0]. Same blog: frameless windows on Linux now get rounded corners by default (`roundedCorners:false` to disable); `view.setBackgroundBlur()` added (platforms not stated).

### Glass / blur
- Windows 11: `backgroundMaterial` option and `win.setBackgroundMaterial(material)`; values auto, none, mica, acrylic, tabbed [V https://raw.githubusercontent.com/electron/electron/main/docs/api/structures/base-window-options.md and https://www.electronjs.org/docs/latest/api/browser-window]. setBackgroundMaterial doc says it is supported only on Windows 11 22H2 and up [V browser-window page]; the Win32 attribute DWMWA_SYSTEMBACKDROP_TYPE needs build 22621 [V search snippet of Microsoft Learn, https://learn.microsoft.com/en-us/windows/win32/api/dwmapi/ne-dwmapi-dwm_systembackdrop_type]. Owner's machine: Windows 11 10.0.26200, so fine.
  - `transparent` on Windows "does not work unless the window is frameless" [V base-window-options.md]. Transparent windows cannot be resized, DevTools open makes them non-transparent, no click-through of transparent area without setIgnoreMouseEvents (Tiro already uses it) [V https://raw.githubusercontent.com/electron/electron/main/docs/tutorial/custom-window-styles.md]. CSS `backdrop-filter`/`blur()` only blurs the window's own content, never what is behind [V same page].
  - Catch 1: backgroundMaterial paints the whole OS window rectangle (620x470 today), not the pill. Acrylic/Mica fills the rectangle, so the glass window must be sized to the visible pill (resize window with the spring, or clip) instead of the current big transparent canvas. Reports of frameless + material needing a patch (Electron "fix: frameless mica/acrylic windows (#39708)", commit mirror https://ayakael.net/mirrors/electron/commit/d1827941790f23b241ef3f234a9782750ac97e8d, with a leftover TODO) [R]. Rounded corners with materials depend on DWM (roundedCorners needs Win 11 build 22000+ [V base-window-options.md]); a custom shape (notch with inverted corners) cannot be done with DWM material and a rectangular window without a window region (setShape is not in the pages I read [U]).
  - Catch 2: acrylic commonly turns off or goes solid when the window is inactive; an always-on-top `showInactive` notch is almost always inactive. Evidence is reports only: Windows Terminal issues #593/#7158/#11092 cited by https://forum.inkdrop.app/t/vibrant-dark-ui-translucent-background-changes-to-opaque-when-switching-to-another-application/3823 and electron-acrylic-window `disableOnBlur` option https://github.com/Seo-Rii/electron-acrylic-window [R]. No Microsoft doc found stating it for DWMWA_SYSTEMBACKDROP_TYPE [U]. Must test on the owner's machine. Mica (not Mica Alt) is documented to follow window activation; acrylic should be tested.
  - Catch 3: inactive/transparent + `alwaysOnTop 'screen-saver'`: Electron doc says levels from pop-up-menu up show above taskbar on Windows; below that, below taskbar [V browser-window page]. 'screen-saver' is already used by Tiro (main.mjs:257).
  - Fallback / alternative: fake glass in CSS (semi-transparent gradient + noise + inner highlight + `backdrop-filter` inside the page, which only blurs page content) = no true desktop blur but works everywhere and on a fixed-size click-through canvas. V-Notch shows a true-blur route (desktop duplication + GPU blur) but needs native code, not practical in Electron without a native module.
- macOS: `vibrancy` option / `setVibrancy` (types such as titlebar, selection, menu, popover, sidebar, under-page; `visualEffectState` followWindow/active/inactive, so use `active` for an inactive notch) [V base-window-options.md, browser-window page]. `type: 'panel'` available on macOS [V]. Native window shadow not shown on transparent windows [V custom-window-styles.md]. Vibrancy fills the window rectangle, same as Windows. macOS 26 "Liquid Glass" has no Electron API that I found [U].
- Linux: no vibrancy or backgroundMaterial; Electron `type` supports desktop, dock, toolbar, splash, notification on Linux [V]. `setAlwaysOnTop` not supported on Wayland [V browser-window page]. Wayland blur needs compositor protocols (KDE kwin blur, new ext-background-effect-v1 landing in GNOME Mutter and KDE Plasma 6.7) [R https://phoronix.com/news/GNOME-Mutter-Background-Blur]; whether Electron 43's `view.setBackgroundBlur(blurRadius)` (needs an alpha background colour [V https://www.electronjs.org/docs/latest/api/view]) works on Linux/Windows/macOS is [U]. Transparent windows on Linux need a compositor; Glasstron README notes Electron Linux transparency bug [R search snippet]. Treat Linux as solid/fake-glass only.
- Verdict: Windows 11 true acrylic/Mica is feasible with the option on a window sized to the pill; macOS vibrancy feasible; Linux CSS-only. Test inactive-window behaviour first.

### FPS / performance of a game (Windows)
- True per-game FPS needs frame (Present) events. Options:
  1. PresentMon (Intel). Licence MIT, (C) 2017-2024 Intel [V https://github.com/GameTechDev/PresentMon, API: 2.7k stars, pushed 2026-11-17]. ETW-based; measures frame times for DirectX/OpenGL/Vulkan; less accurate for OpenGL/Vulkan and with HAGS. No admin needed if the user is in the "Performance Log Users" group (adding needs admin once + sign out); without admin, process info incomplete/short-lived processes show `<unknown>` [V README via https://gitee.com/mirrors/PresentMon and the repo page]. Console app options: `--output_stdout`, `--process_name`, `--terminate_on_proc_exit`, column MsBetweenPresents [V README-ConsoleApplication.md]. ETW kernel logger itself needs admin (Geoff Chappell notes https://geoffchappell.com/notes/windows/etw/security.htm [R]); which session type PresentMon uses [U]. Service version (IntelPresentMon/) adds GPU power/temp/utilisation via vendor APIs. No kernel driver of its own. Redistribution: MIT allows shipping the binary with the notice; separate binary distribution terms not stated [U]. Practical: bundle PresentMon console exe, spawn it from main with --process_name <game>.exe --output_stdout, parse MsBetweenPresents to FPS and 1% lows. Catch: elevation/group setup; AV false positives for ETW tools [U].
  2. RTSS (RivaTuner Statistics Server) shared memory (used by MSI Afterburner, HWiNFO): readable only if the user installed and runs RTSS; freeware, proprietary [R https://www.guru3d.com/files_details/rtss_rivatuner_statistics_server_download.html]. Struct layout (RTSSSharedMemoryV2) and redistribution terms not verified [U]. Reading shared memory from Node needs a native module or a helper (Koffi, like windows-notch-overlay uses for Win32 [V README]). RTSS hooks the game (injection) so anti-cheat can object.
  3. GPU Engine counters (`\GPU Engine(*)\Utilization Percentage`, instances like pid_XXXX_luid_..._engtype_3D): per-process GPU load, no FPS, no admin, readable with PowerShell Get-Counter/typeperf. Instance names must be enumerated; Task Manager shows the busiest engine rather than a sum [R https://learn.microsoft.com/en-us/answers/questions/5641645/how-to-get-the-special-process-gpu-usage-with-the]. Gives GPU load, not FPS.
  4. systeminformation npm: MIT, "dependency free"; "partial Windows" support [V https://systeminformation.io, page does not list which functions]. CPU load, memory, GPU model/util (NVIDIA via nvidia-smi), temps often need extra sensors/admin [U]. It's a new npm dependency (project avoids those); same data is available with PowerShell counters or `nvidia-smi`.
  5. nvidia-smi.exe for NVIDIA GPU util/temp/power (used by windows-notch-overlay [V]); AMD/Intel need vendor APIs.
  6. Overlay-injection approach (Special K, RTSS, Steam/Discord overlays) hooks the swap chain; Discord/Steam overlays work in exclusive fullscreen because they inject [R https://www.th.gl/faq/overlay-not-visible-fullscreen]; kernel-driver tools (HWiNFO sensors) are for temps, not FPS. Not recommended for a proprietary Electron app.
- What gives true FPS vs system load: PresentMon (or RTSS) = real FPS; counters, nvidia-smi, systeminformation = load/temp only. No Windows API gives another process's FPS without ETW Present events or injection.
- macOS: no public per-app FPS API. Metal Performance HUD is per-app (the app/user enables it); Quartz Debug FrameMeter is system-wide refresh; third-party "Count It" attaches to a game [R https://eshop.macsales.com/blog/36772-mac-gaming-see-frames-per-second-in-real-time-with-count-it-app, https://developer.apple.com/forums/thread/676762]. So on macOS show only CPU/GPU/memory/thermals from sysctl/powermetrics (sudo) - [U for details].
- Linux: MangoHud (MIT) is a Vulkan/OpenGL layer you launch the game through (`mangohud %command%`); not system-wide, and not for attaching to an already-running game [V https://github.com/flightlessmango/MangoHud]. For an in-notch FPS number you would need to read its log output; wiring [U].
- Open-source overlays: CapFrameX and OCAT are PresentMon-based [U not fetched; from memory]. Nectar/Lumen/V-Notch/windows-notch-overlay do not show FPS per their READMEs [V].

### Detecting "a game is running"
- Already in the app: `SHQueryUserNotificationState` via PowerShell (main.mjs:497). Values: 2 busy/fullscreen app, 3 D3D exclusive fullscreen, 4 presentation mode, 5 accepts notifications, 7 Store app [V https://learn.microsoft.com/en-us/windows/win32/api/shellapi/ne-shellapi-query_user_notification_state]. Misses borderless-windowed games (they report 5) and flags video players / presentations as "fullscreen".
- Practical heuristics without native modules: (a) process-name list of known games/launchers via `tasklist`/PowerShell `Get-Process` (cheap polling; windows-notch-overlay has a "known-game" notion but how is [U]); (b) foreground window covering a whole monitor via a small PowerShell/C# Add-Type helper (GetForegroundWindow, GetWindowRect, MonitorFromWindow) like the existing PowerShell helper; (c) GPU Engine counter showing a process with sustained 3D load; (d) PresentMon itself lists processes that call Present, which is the most reliable "this process renders frames" signal. Windows Game Mode / Game Bar: no official API found to ask "is a game running"; registry keys HKCU\System\GameConfigStore, GameDVR are settings, not live state [R search, https://windowsreport.com/disable-dvr-windows-11/]. Native module (ffi like Koffi, which windows-notch-overlay uses) would remove the PowerShell spawn cost but adds a dependency.
- Overlay over games: topmost windows cannot draw over a game in exclusive fullscreen (game bypasses compositor); borderless windowed works [R https://www.th.gl/faq/overlay-not-visible-fullscreen, https://forums.codeguru.com/showthread.php?p=1059163]. Modern DX11/12 "fullscreen" is usually flip-model (fullscreen optimisations), where overlays usually do appear, but this is anecdotal [R]. Electron `alwaysOnTop 'screen-saver'` puts the window above taskbar [V]. Nectar hides over any window covering the monitor and warns borderless games may still show it [V]. So: expect the notch to be visible over borderless games, not exclusive fullscreen; do not promise a performance overlay in exclusive fullscreen (needs injection like RTSS/Steam).
- Also note anti-cheat: injection-based overlays can trip anti-cheat; ETW-based PresentMon does not inject [U for specific anti-cheats].

### Calendar sources
- Local .ics file or URL: no account; a parser (ICS recurrence rules are the hard part; npm `node-ical`/`ical.js` is a new dependency [U], or a small hand-written parser limited to simple events). Needs from user: file path or secret ICS URL. Google Calendar "secret address in iCal format" and Outlook "publish calendar" both give ICS URLs: Outlook publishing is in Outlook on the web/new Outlook only; can be disabled by tenant admin and is commonly disabled on work accounts; updates can lag (a university KB says up to 24 h for Google subscribers) [R https://www.ablebits.com/office-addins-blog/make-outlook-calendar-public/, https://kb.wisc.edu/helpdesk//130454]. Link is an anonymous capability URL - must be stored as a secret.
- Microsoft 365 / Outlook via Microsoft Graph: needs an Entra app registration (public/native client, no client secret), redirect URI, delegated scope Calendars.Read + offline_access, user sign-in (auth code + PKCE, MSAL recommended); tenant admin consent may be required [V https://learn.microsoft.com/en-us/graph/auth-v2-user]. the organisation's M365 tenant: IT can register the app; per-user consent policy [U]. Best experience (real events, join links).
- Google Calendar API: Cloud project, enable Calendar API, create "Desktop app" OAuth client, loopback redirect `http://127.0.0.1:port`, PKCE mandatory; request all scopes up front [V https://developers.google.com/identity/protocols/oauth2/native-app]. Unverified apps in Testing status: user limit 100 and refresh tokens expire after 7 days; In production avoids that [R https://support.google.com/cloud/answer/15549945 via search; sensitivity classification of calendar.readonly and verification steps not verified [U]]. For one person: fine in Testing, but re-sign-in weekly.
- OS calendar: Windows has no simple Node-accessible API for the Calendar app (Outlook COM/MAPI from PowerShell is possible, classic Outlook only [U]); macOS EventKit needs a native module or helper binary and a calendar permission prompt [U]; Linux (Evolution/KDE) no common API. Not recommended as the primary route.
- Recommendation: ICS URL first (zero setup, works cross-platform), Graph second (owner uses M365); Google only if asked.
